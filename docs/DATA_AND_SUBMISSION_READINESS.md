# Data, safeguards and submission evidence

## Data handling

Use synthetic demonstration records for the patient journey and disclose that status. Keep imported MRI/OASIS research records separate from the fictional patient unless an explicit, justified association exists. Record dataset release, provenance, permitted uses, attribution and any data-use agreement before redistribution. Do not assume a public download permits all commercial use or that a template is licence-free.

Before enabling a live provider, document exactly which fields leave the server, patient authorization where applicable, contractual terms, hosting region, retention, logging and deletion. Do not send raw MRI, identifiers or unrestricted clinical notes merely because an API key is available. A mock run is labelled as such. Keep keys server-side; exclude credentials, health records and verification exports from shared artifacts.

## Risk register for the pilot

| Risk | Existing control / required next action |
|---|---|
| Unsupported diagnosis or prediction | Research boundaries and grounded draft checks; expert review of all final claims |
| Stale or incompatible evidence | Fingerprints, review digest and protocol separation; show limitations and request a new review |
| Concern mistaken for resolved | Independent statuses; explicit outcome note; define service response and escalation ownership |
| Misheard consequential action | Confirmation and repeat protection; real speech evaluation still required |
| Ambiguous care instruction | Clinician authoring/review; clarify units and schedule before assignment, never infer dosing |
| Unauthorized disclosure | Purpose grants, ownership checks and log masking; independent security review and deployment configuration |
| Provider or network outage | Preserve manual functionality; test actual deployment recovery and establish support procedures |
| Misleading demo evidence | Synthetic/mock labels and separate evaluation categories; no invented accuracy or clinical-benefit numbers |

## Submission preparation

The supplied PowerPoint template has not been filled or modified. Use the following evidence map when the team prepares its submission:

| Template topic | Material to prepare |
|---|---|
| Team and capability | Actual members, roles and relevant experience; team must supply these |
| Problem, users and outcome | Care-loop goal, intended users, current gaps and bounded intended use |
| Architecture | Existing architecture plus linked journeys, evidence checks, agent review and consent boundaries |
| Metrics and evidence | Actual software report; clearly separate planned speech, clinical and usability studies |
| Data and legal basis | Source inventory, licences, synthetic labels and provider data-flow review |
| Risks | Risk register above with accountable owners and residual limitations |
| Access and hardware | Tested demo login, hosting instructions, browser/device requirements and imaging dependencies |
| Pilot | Evaluation plan, recruitment/approvals, support owner, stop rules and proposed comparison |
| IP and conflicts | Team-approved truthful declarations; do not infer or fabricate |
| Video and additional material | One complete fictional journey; confirm official duration and AI narration/avatar rules with organizers |

Neither a strict three-minute rule nor permission for AI-generated narration/avatar is established by this implementation. Confirm those points from the organizers before final submission.
